# ADR-0001: Bus 的所有权

- 状态：Provisional
- 日期：2026-11-19
- 关联：`docs/standard.md` §15.1、§3.6；`docs/roadmap.md` §M4

## 背景

OSAP 需要一个每用户的 Agent Bus，但“谁来拥有它”没有唯一答案：OS 厂商可以把它做成系统服务，桌面环境可以把它做成会话服务，运行时（如 JVM、Node、Python）可以内置一个，也可以由独立守护进程提供。

所有权决定三件事：谁控制升级与默认策略、谁承担 TCB（可信计算基）的安全评审、以及谁能观察跨应用元数据。如果所有权同时带来策略权或签发权，就会出现“平台既当裁判又当运动员”的问题。

## 暂定结论

0.1 **不强制单一所有者**，但强制职责分离：

1. Bus Core 是每用户会话的一个逻辑组件；它可以由 OS、桌面环境、运行时或独立守护进程实现。
2. Bus Core MUST NOT 执行策略、签发能力、解析业务 payload 或持久化审计正文；这些职责属于 Registry、Consent、Capability、Context、Audit。
3. 拥有 Bus Core 的一方 MUST NOT 因此获得以下特权：
   - 替用户做出同意决定；
   - 修改能力衰减规则；
   - 读取它本来无权读取的业务 payload；
   - 在审计链中伪造其他实现的事件。
4. 在 Linux 上，参考实现采用独立守护进程 + `systemd --user`；在 macOS/Windows 上，优先使用平台已有的会话服务或 XPC/named pipe，而不是再引入一个常驻进程。
5. 任何实现声称 “OSAP-compatible” 时，MUST 声明自己的 Bus 所有者与 TCB 边界；不得用“系统内置”作为跳过能力校验的理由。

## 后果

- 允许多个实现并存，有利于互操作与不被单一厂商锁定。
- 需要一致性测试覆盖“不同所有者、同一语义”，尤其是注册、路由、撤销与审计。
- TCB 边界变得更难描述；安全评审必须逐实现进行，不能只评审参考实现。
- 平台内置 Bus 可能拥有更好的对端认证与生命周期管理，但也会带来策略俘获风险；ADR 要求职责分离来限制它。

## 备选方案

- **只允许 OS 厂商拥有**：对端认证最强，但创新与跨平台互操作最慢，且容易把策略权集中到平台。
- **只允许独立守护进程**：中立，但在移动/沙箱平台上难以获得足够的对端凭据与生命周期支持。
- **纯 P2P，无 Bus**：消除中心组件，但发现、配额、撤销传播与审计聚合会退化为每个 Agent 自行实现，难以一致。
- **运行时内置**：部署简单，但一个运行时可能只服务自己的 Agent，跨运行时仍需一个中立层。

## 重审触发条件

出现以下任一情况时，重新打开本 ADR：

1. 任一主流 OS 发布原生 Agent Bus，并希望 OSAP 作为其 wire format；
2. 出现多厂商治理机构，能够统一 Bus 的所有权与策略边界；
3. 有证据表明某个 Bus 所有者利用位置优势读取 payload、操纵同意或压制竞争实现；
4. 一致性测试发现“同一语义、不同所有者”无法互操作。
