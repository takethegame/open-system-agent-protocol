# ADR-0005: 同意疲劳

- 状态：Provisional
- 日期：2026-11-19
- 关联：`docs/standard.md` §15.5、§5.7、§10.2–§10.4；`docs/roadmap.md` §M4

## 背景

“每次动作都问用户”在安全上最保守，但在真实使用中会导致用户不看内容就点允许。反过来，“一次任务级授权”减少打扰，却可能把权限扩大到用户没有预期的地方。OSAP 需要在可理解性、可撤销性与打扰频率之间取得平衡。

## 暂定结论

1. **按风险分级**：
   - L0/L1：自动允许或首次同意；L1 的个人读取 SHOULD 支持任务级授权。
   - L2：自动 + 通知；用户可事后撤销。
   - L3：默认每次同意；允许**有界任务级授权**，但必须带 `task_id`、`max_uses`、`expires_at` 与明确的动作/资源集合。
   - L4：强确认 + 二次认证；不得使用静默的任务级批量授权。
2. **批量同意必须显式**：`allow_task` 只能覆盖请求中列出的动作与资源；不得因为“同一任务”自动扩展到新动作、新资源或新 audience。回执 MUST 记录实际生效的 scope。
3. **不制造暗模式**：同意 UI MUST 同时展示允许与拒绝；不得预选“允许”、不得用倒计时逼迫、不得把“拒绝”藏在二级菜单。拒绝 MUST 是终态，不得静默重试更宽的请求。
4. **可撤销**：用户撤销回执 MUST 立即级联失效相关能力；撤销入口 MUST 与授权入口同样可达。
5. **可度量**：实现 SHOULD 记录同意请求数、允许/拒绝率、平均决策时间与撤销率（不含内容）。如果拒绝率或撤销率异常升高，应视为 scope 或文案有问题的信号，而不是“用户不懂”。
6. **可解释**：请求 MUST 包含 `intent_preview`（actor、what、data、cost、ttl、irreversible），且 preview 必须由 PCS 从能力描述与策略派生，不能只信 Agent 自述。

## 后果

- L3 任务级授权会减少弹窗，但需要更严格的 scope 校验与撤销传播。
- 用户研究成为必要工作；否则“减少疲劳”可能只是“减少可见性”。
- L4 的二次认证会增加摩擦，但这是高风险动作的预期成本。
- 需要 UI 规范或平台指南来约束暗模式；协议本身不能强制视觉设计。

## 备选方案

- **每次动作都问**：最保守，但会迅速产生疲劳，用户会盲目允许。
- **一次授权、永久有效**：最省事，但违反最小权限与可撤销性。
- **完全交给 OS 默认策略**：减少协议负担，但不同 OS 的默认值可能不可比。
- **按 App 而不是按任务授权**：接近现有移动权限模型，但无法表达“这次任务只读这一条记录”。

## 重审触发条件

1. 用户研究显示任务级授权导致误授权或撤销困难；
2. 出现 L3 事故，根因是批量同意 scope 过宽；
3. 监管或平台指南要求更细的同意粒度（如按数据项）；
4. 同意请求量下降到用户不再阅读的程度，说明分级仍不合理。
