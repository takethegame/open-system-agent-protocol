# ADR-0006: 语义发现

- 状态：Provisional
- 日期：2026-11-19
- 关联：`docs/standard.md` §15.6、§6.3–§6.4；`docs/roadmap.md` §M4

## 背景

结构化能力匹配（动作、资源、schema、风险）可解释、可测试，但用户说“帮我安排下周的会”时，能力名称未必包含“安排”或“会”。Embedding/语义检索可以提高召回率，但会把能力描述、资源名称甚至用户查询发往向量模型；如果模型在远端，还会产生隐私与供应链风险。

## 暂定结论

1. **结构化匹配优先**：0.1 的发现 MUST 先按能力记录的结构化字段过滤（动作、资源、schema、风险、可用性），语义排序只能作为**可选后的重排**。
2. **本地、可选、可解释**：
   - embedding 索引 SHOULD 在本地生成与查询；不得把原始能力描述、资源标识或用户查询上传到远端，除非用户显式同意并记录审计。
   - 语义结果 MUST 附带匹配理由（命中的结构化字段、相似片段或分类标签），不能只给一个分数。
   - 语义匹配 MUST NOT 绕过授权、同意、风险或出口策略；它只影响候选顺序。
3. **索引不是权威**：能力记录仍是唯一事实来源；索引是派生数据，必须可删除、可重建、可按用户/App 失效。记录过期或被撤销时，索引 MUST 同步失效。
4. **查询最小化**：查询日志 SHOULD 只保留必要的诊断字段，默认不保留完整自然语言查询；长期保留 MUST 单独授权。
5. **不做跨用户画像**：不得用语义索引把不同用户的能力使用关联成画像；索引按用户分区，跨用户查询 MUST 拒绝。

## 后果

- 没有语义模型时，发现能力较弱；但实现可以选择不启用，不影响一致性。
- 本地 embedding 会增加安装体积与 CPU/内存开销。
- 需要定义“匹配理由”的最小结构，否则 UI 仍可能变成黑盒。
- 远端注册表如果只支持语义搜索，OSAP 只能把它当作候选来源，不能把分数当授权依据。

## 备选方案

- **纯结构化**：最可解释，但召回率低，用户需要知道能力名称。
- **纯 embedding**：召回率高，但不可解释、隐私风险大、难以测试。
- **远端托管向量服务**：部署简单，但把能力图谱与查询暴露给第三方。
- **规则 + 同义词表**：轻量，但维护成本高，跨语言效果差。

## 重审触发条件

1. 出现可在本地运行、隐私可接受的 embedding 模型；
2. 外部注册表要求 OSAP 提供语义查询接口；
3. 用户研究显示结构化匹配的召回率不可接受；
4. 出现语义索引导致的跨用户关联或数据泄漏事件。
