# ADR-0007: 提示注入责任

- 状态：Provisional
- 日期：2026-11-19
- 关联：`docs/standard.md` §15.7、§9.4、§11.1；`docs/roadmap.md` §M4

## 背景

提示注入把不可信内容伪装成指令，诱导 Agent 执行用户没有要求的动作。它可能来自网页、邮件、日历描述、文件名、工具返回，甚至另一个 Agent 的消息。没有任何单一层能完全阻止它：协议看不到语义，App 不能控制模型，模型不能替用户做授权决定。

## 暂定结论

1. **分层责任**：
   - **协议层（OSAP）**：标注 `origin`/`trust`，分离指令与数据，强制能力、audience/task 绑定、同意与审计；对来自 `external` 的内容默认 `unverified`，高风险动作必须经过同意。
   - **App/内容层**：对外部内容做来源标注、清洗与隔离；不得把外部文本直接拼进系统指令；对文件、邮件、网页提供可验证的来源。
   - **模型/运行时层**：实现指令层级、工具调用策略、上下文隔离与输出过滤；不得把“模型判断安全”当作唯一闸门。
2. **协议不承诺“防注入”**：OSAP 的目标是**限制爆炸半径**，不是识别所有注入。文档与实现 MUST NOT 声称“启用 OSAP 即可防止提示注入”。
3. **动作闸门**：由不可信内容触发的 L3/L4 动作 MUST 重新征得同意，并在 `intent_preview` 中显示数据来源与目标；不得沿用之前为其他任务发放的能力。
4. **来源标签不可伪造**：`origin`、`trust`、`derived_from` 由 Context Fabric 或桥接器写入，Agent 不得自行提升。外部内容默认 `trust=unverified`，标签冲突取更严格值。
5. **审计可追溯**：每个由外部内容触发的动作 SHOULD 记录 `context_refs` 与来源摘要，便于事后定位是哪个网页/邮件/文件触发了动作。

## 后果

- 仍会有注入成功案例；责任划分必须写进安全文档，避免“协议背锅”或“模型背锅”。
- 需要 App 与运行时配合；仅部署 OSAP 不会自动提高内容安全。
- 同意 UI 需要显示“这条内容来自外部”，否则用户无法判断。
- 安全评审应把注入当作持续风险，而不是一次性漏洞。

## 备选方案

- **协议层做内容扫描**：会引入语义判断、隐私与误报，且 Bus 不应解析 payload。
- **完全交给模型**：模型可被绕过，且无法替用户授权。
- **完全禁止外部内容**：不现实，跨应用任务的核心就是处理外部内容。
- **只做审计、不做闸门**：事后可见，但不能阻止副作用。

## 重审触发条件

1. 出现可复现的 Agent 注入基准，能比较不同分层策略；
2. 平台提供指令来源或内容 provenance 的标准机制；
3. 出现新的注入载体（如工具描述、能力记录、审计导出）；
4. 安全评审发现现有标签/闸门可被绕过。
