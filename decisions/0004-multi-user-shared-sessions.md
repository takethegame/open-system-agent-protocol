# ADR-0004: 多用户共享会话

- 状态：Provisional
- 日期：2026-11-19
- 关联：`docs/standard.md` §15.4、§3.6、§10.8；`docs/roadmap.md` §M4

## 背景

桌面会话不总是“一人一机一登录”。快速用户切换、远程桌面、多 seat、共享 kiosk、以及企业“托管设备 + 个人会话”都会让多个主体在同一台设备上交替出现。如果 Bus 把“当前登录用户”当作唯一主体，任务、能力、上下文句柄与审计就可能跨主体泄漏。

## 暂定结论

1. **每用户一个 Bus 实例**。0.1 不支持跨用户共享一个 Bus；不同 uid 的 Bus MUST 隔离状态、队列、审计与能力存储。
2. **主体切换 = 新会话**。快速用户切换或远程会话切换 MUST 创建新的 `session_id`；旧会话的能力、任务与句柄 MUST NOT 自动迁移到新会话。需要继续的任务 MUST 通过显式 handoff 或重新授权。
3. **能力绑定用户与会话**。能力 token 的 `issuer`/`subject` 与回执的 `user` MUST 能追溯到具体主体；`session_id`（若存在）MUST 匹配。不得用“设备已解锁”代替主体绑定。
4. **共享 kiosk**：0.1 只允许一个专用用户或一个显式的单主体会话。多主体共享会话（同一 OS 会话内切换主体）列入 0.2；在 0.2 之前，实现 MUST NOT 声称支持。
5. **数据边界**：审计、上下文事件、能力签发/撤销、同意回执 MUST 按用户分区；跨用户查询 MUST 经过显式授权并记录审计。`task://` 黑板与 `ctx://` 句柄 MUST NOT 跨用户解析。
6. **通知与可见性**：用户 MUST 能查看“当前有哪些 Agent 在运行、持有哪些能力”；切换用户后，UI MUST NOT 显示上一个用户的能力或审计。

## 后果

- 资源使用增加（每个用户一个 Bus），但隔离清晰。
- 快速切换用户时，后台任务可能被中断；需要明确的恢复/取消策略。
- 企业共享设备需要专用账号或 0.2 的多主体模型，不能靠“共用管理员账号”绕过。
- 审计导出必须带用户范围，避免把不同主体的记录混在一个可读视图中。

## 备选方案

- **单 Bus 多主体**：节省资源，但状态隔离、撤销传播与审计分区都更复杂，0.1 无法安全实现。
- **设备级 Bus + 主体标签**：适合 kiosk，但容易把“设备解锁”误当成“主体授权”。
- **完全禁止共享设备**：不现实，且会把用户推向更不安全的绕过方式。

## 重审触发条件

1. 远程桌面或多 seat 成为主要使用场景；
2. 企业共享设备需要同一 OS 会话内切换主体；
3. OS 提供 per-app 用户上下文或强制的应用级主体隔离；
4. 出现跨用户数据泄漏或审计混读事件。
